# Spring (Java) 学習記録

SES待機期間中の自己学習リポジトリです。
Spring Bootの習得を目指します。

## 毎日の学習ログ

### 2026-09-11
* **やったこと**: 
  * *プロジェクトの立ち上げとCLI操作*:
    * Spring Initializrを利用し、MavenベースのSpring Bootプロジェクトを生成。二重ディレクトリの問題を cd コマンドで自己解決し、mvnw.cmd によるサーバー起動を実践。
  * *ルーティングと基本応答*:
    * @RestController と @GetMapping を使い、ブラウザからのリクエストに対して文字列を返す基本のAPI（/hello）を構築。
  * *オブジェクトのJSON自動変換*:
    * UserProfile クラスや ArrayList を作成。Getterを定義しておくだけで、Javaのオブジェクトが自動的にJSONのオブジェクト（{}）や配列（[]）としてフロントエンドに配信される仕組みを実装。
  * *HashMapを使った簡易DB検索API*:
    * 「もふ」「たま」「ぽん」といったペットの名前をキー、品種を値とする HashMap を構築。@PathVariable でURLから検索キーを受け取り、該当データを返す PetController を作成。
  * *エラーハンドリング*:
    * 登録されていないキー（例：「ポチ」）で検索された際の条件分岐を作成し、APIの堅牢性を確保。
  * *バージョン管理*:
    * 実装済みのコードを spring-study という適切な名前に変更し、GitHubへプッシュ完了。
* **気づき・他言語（LaravelやNext.js）との違い**
  * *ルーティングの集約（アノテーション）*:
    * Laravel（routes/web.phpで一元管理）やNext.js（ファイルやフォルダ構造がそのままURLになる）とは異なり、Spring Bootはクラスやメソッドの真上に @GetMapping("/pets/{name}") のように「目印（アノテーション）」を書くだけで完結します。処理とURLの対応がひと目でわかるのが特徴です。
  * *JSON生成のアプローチ（厳格さと自動化）*:
    * PHPの連想配列やTypeScriptのオブジェクトのように「直接JSONっぽい形を書く」のではなく、Javaでは「必ずクラス（設計図）を作り、Getterを用意する」という手順を踏みます。少し手間はかかりますが、「型」が絶対的に保証されるため、大規模開発でもバグが起きにくいという強みがあります。
  * *基礎文法と実務の直結*:
    * 今日学んだ ArrayList や HashMap が、単なるコンソールの文字遊びではなく、Web APIが返す「JSONの配列」や「データベースの代わり」としてそのまま機能することが体感できました。

### 2026-09-14
* **やったこと**: 
  * *データの登録API（POST）の実装*:
    * @PostMapping と @RequestBody を使い、JSONデータを受け取って HashMap （簡易データベース）に追加する機能を作成した。
  * *受け取り専用クラスの作成*:
    * フロントエンドからのデータを受け止める専用クラス（PetRequest）を作成し、Javaの厳格な型ルールに則った安全なデータ受信を実装した。
  * *REST Clientによるテスト*:
    * VSCode拡張機能「REST Client」を導入し、api.http ファイルからPOST/GETリクエストを送信。ブラウザではできない「登録処理」の動作検証を行った。
  * *レイヤーアーキテクチャへのリファクタリング*:
    * 処理を「窓口（Controller）」と「ビジネスロジック（Service）」に分離。@Service を付与した PetService クラスにデータ処理を切り出し、実務標準の設計思想を適用した。
  * *トラブルシューティングの実践*:
    * ジェネリクス（``）の指定漏れによるコンパイルエラーや、PCのメモリ不足によるサーバー起動エラーに直面し、自力で解決した。
* **気づき・他言語との違い**:
  * *型（ジェネリクス）の厳格さと安全性*:
    * PHP（Laravel）やTypeScriptのようにリクエストデータを柔軟なオブジェクトや連想配列としてそのまま受け取るのではなく、Javaでは「受け取り専用クラス」を定義し、Mapのキーと値も `` と明確に指定する必要がある。記述量は増えるが、型不一致などのバグをコンパイル時点（実行前）で確実に防げる堅牢さを肌で感じた。
  * *アーキテクチャによる役割分担の美しさ*:
    * Controller（窓口）とService（厨房）を分けることで、各クラスの役割が極めて明確になった。LaravelなどでもService層を分けるアプローチはあるが、Spring Bootでは @Service などのアノテーションとDI（依存性の注入）によって、この連携が非常にスムーズに実現できることがわかった。
  * *API設計とテストツールの必須性*:
    * ブラウザのURL直打ち（GET）だけではPOST処理の検証ができないため、REST Clientのようなツールが不可欠であることを学んだ。また、作成した .http ファイルがそのまま「APIの使い方メモ（仕様書）」としてGitに残せるという実務的なメリットを体感できた。

### 2026-09-16
* **やったこと**: 
  * *CRUDの完全実装*:
    * 既存のGET（取得）・POST（登録）に加え、@PutMapping での更新処理と @DeleteMapping での削除処理を実装。Web APIの基本となる4大操作（CRUD）を完成させた。
  * *Repository層（3層アーキテクチャ）の導入*:
    * データ操作を専門に行う PetRepository クラスを新設。処理を「Controller（窓口）→ Service（ビジネスロジック）→ Repository（データ操作）」の3層に完全分離した。
  * *REST Clientを用いたAPIテストの効率化*:
    * VSCode拡張機能「REST Client」を活用し、api.http ファイルに複数のテスト項目を記述。連続したテスト実行と、API仕様書としての活用方法を学んだ。
* **気づき・他言語との違い**:
  * *レイヤーアーキテクチャ（階層設計）の絶大な効果*:
    * Repository層にデータ処理を切り出した際、窓口であるControllerのコードを1文字も書き換えずに済んだことに感動した。各クラスの役割（責務）を明確に分けることで、将来データベースをMySQLなどに変更しても影響を最小限に抑えられる「実務の美しい設計」のメリットを肌で実感できた。
  * *Javaの厳格な型指定（ジェネリクス）*:
    * Map のように型を厳格に指定しないとコンパイルエラーになる。柔軟な言語（PHPやTypeScript）に比べると記述量は増えるが、事前にバグを防ぐ堅牢さを再び体感した。
  * *テストツールの利便性*:
    * api.http に ### で区切って複数のリクエストを書いておけば、それがそのまま「APIの使い方マニュアル」になり、チーム開発でも非常に役立つツールだとわかった。

### 2026-09-17
* **やったこと**: 
  * *バリデーション（入力値チェック）の導入*:
    * pom.xml に spring-boot-starter-validation の依存関係を追加し、APIの入力値チェック機能を有効化した。
  * *アノテーションによるルールの定義と適用*:
    * リクエストを受け取る PetRequest クラスのフィールドに @NotBlank を付与して必須ルールを設定。さらに、Controller側の引数に @Valid を追加し、受信時にチェックが発動するよう紐付けた。
  * *不正なリクエストの防御テスト*:
    * api.http を用いて意図的に「空文字」を含むJSONを送信し、400 Bad Request として正しく弾かれる（Controller層でブロックされる）ことを確認した。
  * *Docker / WSL2 を用いたMySQL環境構築*:
    * 時間を要したがDocker Desktopをインストール。コマンド1行でMySQLコンテナを起動し、開発用のデータベース（spring_db）を用意した。
  * *Spring Data JPAによるデータベース連携*:
    * 簡易辞書（HashMap）でのデータ管理から、本物のMySQLデータベースを用いたデータの永続化（CRUD処理）へとシステムを移行した。
* **気づき・他言語との違い**:
  * *宣言的プログラミングの便利さ*:
    * if (name == "") のような条件分岐を自分で書く必要がなく、タグ（アノテーション）を付けるだけで強力なチェックが働くSpring Bootの仕組みに感動した。
  * *入り口で弾く重要性*:
    * 不正なデータが Service や Repository（辞書）に到達する前に、最初の関所である Controller でブロックすることの重要性と、そのための具体的な実装方法を体感できた。
  * *3層アーキテクチャの真価*:
    * データをHashMapからMySQLへ移行するという「裏側の大きな改修」を行ったにもかかわらず、窓口である「Controller」のコードは1文字も変更せずに済んだ。レイヤーを分割して責務を分ける設計の美しさと、実務における保守性の高さを肌で実感した。

### 2026-09-24
* **やったこと**: 
  * *例外処理の共通化とJSON整形*:
    * @RestControllerAdvice を用いて、アプリ全体のエラーを監視する司令塔（GlobalExceptionHandler）を作成。バリデーションエラーをフロントエンドが扱いやすいJSON形式に変換して返す仕組みを実装。
  * *Swagger（OpenAPI）の導入*:
    * pom.xml に依存関係を追加し、API仕様書とテスト画面をブラウザ上で自動生成する環境を構築。
  * *依存関係（バージョン）のトラブルシューティング*:
    * ツール導入時に発生したエラーログ（NoSuchMethodError）を読み解き、Spring Boot本体とSwaggerのバージョン不整合を特定・解決した。
* **気づき・他言語との違い**:
  * *アノテーションによる横断的関心事の分離*:
    * 各Controllerに都度 try-catch を書かなくても、@RestControllerAdvice をつけるだけでアプリ全体のエラー処理を一箇所に集約できる。これにより、Controllerのコードを非常にクリーンに保てるSpring Bootの設計の美しさを学んだ。
  * *APIドキュメント生成の手軽さ*:
    * ゼロから仕様書を書かなくても、1行コードを足すだけでフロントエンド向けの立派なテスト画面（Swagger UI）が完成することに驚いた。
  * *エコシステムのバージョン管理*:
    * ライブラリを追加した際、フレームワーク本体とのバージョンが噛み合わないとパニック（500エラー）が起きるという「依存関係の壁」を実体験し、ログから原因を特定する実務的なデバッグ手法を学んだ。

  *
